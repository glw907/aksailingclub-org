## Filed during execution (2026-08-21)

1. **The `./sveltekit` barrel is the only route to `createD1AuditSink`, and a new re-export in
   0.95 broke a raw, non-Vite consumer of it.** This site's `src/jobs/runner.ts` imports
   `createD1AuditSink` from `@glw907/cairn-cms/sveltekit`, the package's own barrel
   (`dist/sveltekit/index.js`), which is the only exported path to that function; there is no
   narrower subpath export for it. `runner.ts` is deliberately bundled outside Vite, by
   `scripts/wire-scheduled-handler.mjs`, which appends a raw import of that file straight into
   the built Worker so a Cloudflare Cron Trigger handler can be wired onto
   `@sveltejs/adapter-cloudflare`'s generated `_worker.js` (the adapter overwrites `main` on
   every build, so a checked-in wrapper file cannot survive). Wrangler bundles that one file
   with its own plain esbuild pass at `wrangler dev`/`wrangler deploy` time, with no SvelteKit
   Vite plugin available to it.

   As of cairn 0.95.0, the `./sveltekit` barrel also re-exports `previewLoad`/`mintPreviewToken`
   (`dist/sveltekit/preview.js`), the share-a-draft preview feature. `preview.js` reads
   `building` from `$app/environment`, a SvelteKit virtual module. Importing one name from a
   barrel pulls in every other export's own dependencies too, so wrangler's esbuild pass, asked
   to bundle `runner.ts`'s import of `createD1AuditSink`, walks the whole barrel and fails to
   resolve `$app/environment`, a module only Vite's SvelteKit plugin knows how to resolve.

   **Evidence.** `npx wrangler deploy --dry-run` (and equally `wrangler dev --local`) fails
   with:

   ```
   ✘ [ERROR] Could not resolve "$app/environment"

       node_modules/@glw907/cairn-cms/dist/sveltekit/preview.js:10:25:
         10 │ import { building } from '$app/environment';
   ```

   This reproduces on a clean build with no preview route wired on this site's side at all;
   it is purely a consequence of the barrel gaining a new `$app/environment`-dependent export.
   `npm run check`, `npm test`, and `npm run build` all stay green throughout, since none of
   them invoke wrangler's own bundler; only `wrangler dev`, `wrangler deploy`, or a Playwright
   run whose `webServer` starts `wrangler dev` surfaces it. That gap means a future barrel
   addition with the same shape can pass every gate a consuming site normally trusts and still
   break its actual deploy.

   **Proposed engine fix.** Either a `./sveltekit/audit-sink` subpath export, so a consumer
   that wants only `createD1AuditSink` never pulls in the rest of the barrel's dependency
   surface, or a lazy read of `building` inside `previewLoad` (a dynamic `await
   import('$app/environment')` at call time, or reading it from the passed-in `event`/`runtime`
   instead of a module-level static import) so the barrel's own top-level import graph never
   touches a SvelteKit virtual module merely by being re-exported.

   **Site-side workaround**, not a substitute for the engine fix: a `wrangler.toml` top-level
   `[alias]` entry (esbuild's own alias config) pointing `"$app/environment"` at a small local
   shim exporting the correct runtime values (`building`/`browser`/`dev` all `false`, since by
   the time a Worker is actually executing, the SvelteKit build has already finished). Scoped
   in practice to the one raw-bundled file, since the Vite-built server output already resolves
   `$app/environment` correctly everywhere else.

2. **`previewLoad` hands back a raw `seo` (`canonical`, `og:url`, `jsonLd.url` all still pointing
   at the entry's eventual permalink); every adopter of the preview feature has to rediscover
   independently that a preview render needs those three fields stripped before it reaches its
   own head component.** This site did (`ArticleView.svelte`'s `preview` flag, backed by the new
   `previewSafeSeo` in `src/theme/preview-seo.ts`), but nothing in `previewLoad`'s own contract
   says a caller must, and the showcase's own reference `ArticleView` got the mechanism wrong in
   its comments while doing the right strip: it claimed the URL itself is the bearer credential
   ("a preview link is a bearer credential ... so on preview this component strips `canonical`
   ... the URL is the credential, and a site's own chrome otherwise exports it to every third
   party the site reports to"). The token is the credential; the canonical/og:url/jsonLd.url URL
   is the entry's ordinary, already-computed public permalink, present whether or not the entry
   has ever published. Stripping it is about not letting a crawler or unfurler consolidate the
   preview onto a not-yet-live URL, and not letting the page self-canonicalize while it is
   `noindex`ed, not about hiding the token, which lives only in the route path and never in the
   page. **Proposed engine fix.** `previewLoad` returns the `EntryData` it already resolved, so
   it could hand back a `seo` field pre-stripped of `canonical`/`og:url`/`jsonLd.url` (or a
   `previewSafeSeo(seo)` export consumers call once, the same shape this site landed on), so a
   new adopter gets the correct behavior and the correct reason without re-deriving either.

3. **`PreviewBanner` keys its dark palette off `prefers-color-scheme`, not the host site's own
   theme toggle.** Its four custom properties (`--cairn-preview-bg`, `--cairn-preview-fg`,
   `--cairn-preview-border`, `--cairn-preview-link`) fall back to literal light-mode hex values by
   default, with a second literal set inside `@media (prefers-color-scheme: dark)`. A site that
   themes by `data-theme` (this one: `theme-toggle.ts`'s explicit flip, `:root[data-theme='asc-dark']`)
   rather than only the OS preference can land a visitor on the toggle's dark mode while the OS
   preference stays light, in which case the banner renders its light literals against the site's
   own dark chrome, or the reverse. This site worked around it by declaring the four properties
   itself in `theme.css`, in the light `:root` block and in both dark selectors (the
   `prefers-color-scheme` block and the `data-theme` block), so the banner always follows
   whichever the site's own toggle is doing. **Proposed engine fix.** Document the four property
   names as the intended site-override seam more prominently (the component doc comment already
   half-says this), or offer a small opt-in companion stylesheet a `data-theme`-based site can
   import instead of hand-declaring the properties itself.

4. **`PreviewBanner` formats the expiry with `new Intl.DateTimeFormat(void 0, { dateStyle:
   'medium', timeStyle: 'short' })` inside a `$derived`, which runs identically during SSR and
   during hydration, so a server whose runtime locale/timezone differs from the browser's own
   (the common case for a Cloudflare Worker versus a visitor's device) can render two different
   expiry strings and produce a hydration mismatch.** The component has no props for this today;
   its only input is the `preview` object. **Proposed engine fix.** Render the expiry as
   `<time datetime={preview.expiresAt}>` with a fixed, locale-independent server-formatted string
   (an ISO-ish or UTC-anchored form computed once, not through the ambient locale), or accept an
   optional `formatExpiry` prop so a site can supply its own stable formatter (this site's own
   `src/chassis/date.ts` already carries exactly that kind of fixed vocabulary for its other date
   surfaces).

5. **cairn's dist `.d.ts` files import directly from `@cloudflare/workers-types`
   (`env.d.ts`, `sveltekit/audit-sink.d.ts`, `sveltekit/platform-bindings.d.ts`,
   `sveltekit/preview.d.ts`, `auth/store.d.ts`, `auth/preview-store.d.ts`,
   `auth-channel/store.d.ts`, `auth-channel/factory.d.ts`, `media/store.d.ts`), so a site that
   generates its own binding types with `wrangler types` (the now-recommended replacement for
   installing `@cloudflare/workers-types` directly) and does not also separately install the
   package loses every cairn-typed `D1Database`/`R2Bucket`/`RateLimit` signature to an
   unresolvable-import `any`, silently: with `skipLibCheck: true` (this site's own setting, and a
   common one), TypeScript suppresses the diagnostic entirely rather than surfacing a red
   `TS2307`, so nothing in `npm run check` flags the degradation. This site rediscovered the
   package as a required (dev)dependency after a toolchain-bump pass dropped it on the assumption
   that `wrangler types` alone was a full replacement; re-adding it (confirmed via a one-off
   `skipLibCheck: false` run: 4 `TS2307`s on cairn's own `.d.ts` files with the package absent,
   0 with it installed) restored real typing with no source change on this site's side.
   **Proposed engine fix.** Reference the Cloudflare runtime types as ambient globals (as
   `wrangler types`-generated projects already have them, avoiding the import entirely) rather
   than importing named types from the package, or declare `@cloudflare/workers-types` a
   `peerDependency` so an adopter's own install step surfaces the requirement instead of a silent
   type gap.
