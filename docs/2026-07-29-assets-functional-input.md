# The Assets functional input packet

The functional briefing the Assets design-capture trial's brainstorm opens against. It records what
the Assets surfaces do today, what the live data actually holds, and which questions only Geoff can
settle. It is deliberately **functional only**: the trial's control conditions (see
`docs/plans/2026-07-29-cairn-design-trial-assets.md`) make cairn's packaged capture the only
sanctioned carrier of design content to a builder, so this file states defects and never remedies.
Anything design-shaped that lands here later is a control violation.

Produced 2026-07-29 by six independent read-only discovery agents plus a synthesizer, each required
to cite `file:line` or a live query for every claim. Live counts were queried against `asc-club`
remote, read-only. Two claims in
`docs/design-benchmark/2026-07-29-assets-trial-log.md` are corrected here, both in the defect
inventory: the chip measured at 1.15 is the payment-standing badge rather than the asset-type chip
(defect 11), and the "square-cornered pagination button" advisory cannot be attributed to any
control on this perimeter, since no `Pagination` component is imported by any of its files
(defect 12).

## What exists today: surfaces, actions, states

Three admin-reachable surfaces touch club assets, plus one member-facing surface outside the admin perimeter.

**`/admin/club/assets`** (`src/routes/admin/club/assets/+page.svelte`, server `src/routes/admin/club/assets/+page.server.ts`) is the direct-management screen. It renders three tab views over one shared query, `listActiveAssignments`: "By asset" (grouped per asset type, with household, description, payment-standing badge, Record payment and Release actions per row, and a per-type assigned-vs-capacity count in the header), "By person" (the same rows grouped by household instead), and "Waitlist" (a single queue spanning all four asset types, showing type, position, member, requested date, with Move-to-end and Remove actions) (`src/routes/admin/club/assets/+page.svelte:21-28,158-311`). Every write on this screen is a server action gated by `clubAdminAction`, which checks an Administrator/Club-manager role via `canReach`, applies a per-editor rate limit, and audits the action (`src/routes/admin/club/assets/+page.server.ts:61-166`; `src/admin-club/lib/club-action.ts:87-128`). The six actions are: assign, release, recordPayment, waitlistAdd, waitlistRemove, waitlistMoveToEnd, and test coverage exists for all six including their failure paths (`src/tests/assets-actions.test.ts:47-199`).

Assign requires an asset type and a membership id (the household's current-season membership; description is optional), and always attaches to a membership rather than a bare member (`src/routes/admin/club/assets/assets-form-input.ts:11-23`; `src/admin-club/lib/assets-store.ts:189-201`). Release is a soft status flip (`active` to `released`), history-preserving, confirmed client-side, with a precondition read that 404s if the assignment no longer exists (`src/routes/admin/club/assets/+page.server.ts:76-93`; `src/admin-club/lib/assets-store.ts:203-208`). Record payment is an upsert keyed on (assignment, season): recording twice for one season corrects the existing row rather than duplicating it; method is card, check, or cash, amount must be a positive whole number, and there is no separate "billed" action distinct from "paid"—recording a payment always stamps `paid_at = now` (`src/admin-club/lib/assets-store.ts:210-239`; `src/routes/admin/club/assets/assets-form-input.ts:25-38`). Payment standing itself is never a stored flag; it is derived at read time into one of three states—not-billed (no payment row this season), outstanding (a row exists with `paid_at` null), paid (`paid_at` set)—and rendered as a badge (`src/admin-club/lib/assets-store.ts:24-29,140-153`; `src/routes/admin/club/assets/+page.svelte:30-34,181-188`).

Waitlist add requires an asset type and a member id (the waitlist attaches to a member directly, unlike an assignment, which attaches to a membership); new entries always land at the tail, computed as `MAX(position)+1` per asset type, and the waitlist never resets across seasons, unlike the class waitlist (`src/admin-club/lib/assets-store.ts:63-81,278-295`; `migrations/asc-club/0007_assets_email/forward.sql:62-63`). Move-to-end re-tails one entry past every other entry in its own asset type's queue and 404s if the entry no longer exists (`src/admin-club/lib/assets-store.ts:302-321`; `src/routes/admin/club/assets/+page.server.ts:148-165`).

The assign and waitlist-add forms use client-filterable native `<select>` pickers with no server-side search, built from `listMembershipOptions`/`listMemberOptions`; the module's own comment states these are appropriate only "at the club's real scale (~93 memberships)" (`src/admin-club/lib/assets-store.ts:166-187`; `src/routes/admin/club/assets/+page.svelte:61-80,109-128`). Empty states are explicit per tab ("No one holds this asset right now," "No household holds an asset right now," "No one is waiting for an asset right now"), and a form-level error banner renders on any action failure (`src/routes/admin/club/assets/+page.svelte:152-156,194-198,248-253,290-294`). There is no pagination anywhere on this screen—every group renders its full result set in one page load—and no search/filter box on the by-asset/by-person/waitlist lists themselves, only on the two inline forms (`src/routes/admin/club/assets/+page.svelte:1-364`).

There is no admin screen or write path anywhere in the codebase to create, edit, or delete an `asset_types` row. A grep of `src/routes` and `src/admin-club/lib` for writes to `asset_types` outside the one-time import script returns nothing; the four existing rows were inserted once by that script and have never been touched by any admin action since (`scripts/import/ops-assets.mjs:590,598`; `migrations/asc-club/0007_assets_email/forward.sql:9`).

**`/admin/club/asset-requests`** (`src/routes/admin/club/asset-requests/+page.svelte`, server `src/routes/admin/club/asset-requests/+page.server.ts`) is a review inbox listing every request with `status='pending'`, oldest first, showing asset type, household, a kind badge ("New"/"Retention"), requester and timestamp, an optional note, and an optional prior-holding summary line (`src/routes/admin/club/asset-requests/+page.svelte:37-53`; `src/member-portal/lib/assets.ts:224-267,269-294`). A "new" request has one Approve button: if the asset type has a free slot the household is assigned directly and the request marked `assigned`; otherwise the requester is enqueued onto that type's waitlist and the request marked `queued` (`src/member-portal/lib/assets.ts:296-336`). A "retention" request's button reads "Approve (opens pay task—$\<fee\>)" and only flips status to `approved_awaiting_payment`; it never assigns outright, assignment happens later only when the member pays, via a function that lives in the member-portal, not this screen (`src/member-portal/lib/assets.ts:338-354,379-404`). Deny (either kind) requires a non-empty reason and sets `status='denied'` with the reason recorded; the dialog's own copy states that notifying the household is a manual step today (`src/routes/admin/club/asset-requests/+page.svelte:75-93`; `src/member-portal/lib/assets.ts:356-365`). Each approve/deny function independently re-checks the request is still pending and matches the expected kind before acting (`src/member-portal/lib/assets.ts:304-336,345-354,358-365`). This screen has one empty state, a top stat tile showing the raw pending count, no pagination, and no filtering or sorting beyond the fixed oldest-first order (`src/routes/admin/club/asset-requests/+page.svelte:21-35,95-99`).

A third, read-only surface exists outside these two screens: the household desk at `/admin/club/members/[id]` renders an Assets panel listing every assignment for that household, active and released alike (unlike the Assets screen's active-only lenses), commented explicitly as read-only ("asset management keeps its own screen") (`src/routes/admin/club/members/[id]/+page.svelte:383-403`; `src/admin-club/lib/households-store.ts:385-397,460-478,503-511`). The Members list also shows a "Holding assets" filter facet and active-only holding chips per expanded household row, sourced from a separate query that mirrors, rather than reuses, the Assets screen's active-assignment lens (`src/routes/admin/club/members/+page.svelte:34,158,320`; `src/admin-club/lib/households-store.ts:60-70`).

The Club section landing page shows a live pending-asset-requests count in its attention strip, linking to the requests inbox; the same count drives a sidebar nav badge, both fed from one shared source so they cannot disagree (`src/routes/admin/club/+page.svelte:14,27-32`; `src/routes/admin/club/+page.server.ts:1-22`; `src/theme/admin-attention.ts:22,36,44,130`). Both screens are registered as separate sidebar entries, "Assets" and "Asset requests," deliberately relabeled from a plain "Requests" to read distinctly (`src/theme/cairn.config.ts:57-60`).

## The real data (live shape, not the schema's aspiration)

Live counts, queried this session against `asc-club` (remote, read-only):

|---|---|---|
| `asset_types` | 4 | mooring, rv_parking, boat_parking, small_boat |
| `asset_assignments` | 90 (41 active, 49 released) | mooring 9 active/8 released; rv_parking 10 active/14 released; boat_parking 19 active/24 released; small_boat 3 active/3 released |
| `asset_payments` | 80 (42 outstanding, 38 paid; not season-scoped) | 76 rows method='card', 4 rows method NULL despite a stripe_ref |
| `asset_waitlist` | 0 | never exercised against real data |
| `asset_requests` | 0 | never exercised against real data |

Two of the four asset types already exceed their stated capacity: rv_parking has 10 active assignments against a capacity of 5, and boat_parking has 19 active against a capacity of 15 (`npx wrangler d1 execute asc-club --remote --command "SELECT asset_type,status,COUNT(*) n FROM asset_assignments GROUP BY asset_type,status;"`; `migrations/asc-club/0007_assets_email/forward.sql:28-34`). Mooring (9 active/capacity 12) and small_boat (3 active, no capacity) are within bounds. Both over-capacity rows predate any capacity-aware admin action—they came from the one-time import—and the approval code's own capacity check (`hasFreeSlot`) would refuse to assign further into either type until releases bring it back under capacity.

Two lenses report an older figure, "40 active assignments span 148 households," dated to a 2026-07-16 portal-design measurement (`docs/design-benchmark/decisions.md:242-246`). The live figure queried this session is 41 active assignments; household count was not re-verified this session. The two numbers come from different points in time and are reported as such, not reconciled.

The four `asset_types` ids in the live database are `mooring`, `rv_parking`, `boat_parking`, `small_boat`, copied verbatim from the club's prior ops database by the one-time import script with no normalization (`scripts/import/ops-assets.mjs:102-103,590,598`). Every consumer of this value in code—the `AssetKind`/`DocumentAudience` type union, all six published 2026 waiver documents, and the requirement-matching code—expects hyphenated ids: `mooring`, `rv-parking`, `boat-parking`, `small-boat-rack` (`src/theme/documents.ts:21-33`; frontmatter of the six document files under `src/content/documents/`). No mapping or normalization function exists anywhere in the repo; every read site does a bare `as AssetKind` cast on the raw column value (`src/member-portal/lib/waiver-requirements.ts:346`; `src/admin-club/lib/documents-store.ts:209`; confirmed absent by grep across `assets.ts`, `assets-store.ts`, `documents-store.ts`). Because `mooring` has no internal separator it matches by coincidence; the other three never match (`rv_parking` vs `rv-parking`, `boat_parking` vs `boat-parking`, and `small_boat` vs `small-boat-rack`, not even the same word).

`settings.current_season` is live `'2026'`, matching the six published waiver documents' season, so this is a live defect, not a dormant one (`npx wrangler d1 execute asc-club --remote --command "SELECT value FROM settings WHERE key='current_season';"` → `2026`). Querying live data this session, 21 distinct households currently hold an active assignment of one of the three mismatched types. For those households, the type-specific acknowledgement document and the shared Dry Storage Agreement requirement (also keyed on the hyphenated form) never appear on any signing list and never gate the asset-fee payment step; the household reads as fully signed when it is not (`src/member-portal/lib/waiver-requirements.ts:36,182-195,234-240`). The unit test suite does not catch this because it feeds the pure requirement-derivation function synthetic, already-hyphenated `assetKinds` arrays, never exercising the real database-to-`AssetKind` cast (`src/tests/member-portal-waiver-requirements.test.ts:110-115,135,233-268`).

A separate, smaller data gap: the import script's `INSERT INTO asset_payments` never populates the `method` column, so any payment row inserted since the schema added that column silently omits it—4 of 80 live rows have `method` NULL despite carrying a Stripe reference (`scripts/import/ops-assets.mjs:640`; confirmed live).

## The request lifecycle as implemented

A member submits a request from `/my-account/gear`, a fully-wired portal surface distinct from the admin's direct-assign screen, backed by the same live tables with no mock data (`src/routes/(site)/my-account/gear/+page.server.ts:1-75`; `src/routes/(site)/my-account/gear/+page.svelte:1-289`). Three member-initiated form actions exist—`releaseAsset`, `cancelRequest`, `requestAsset`—each scoped to the caller's own household (`src/routes/(site)/my-account/gear/+page.server.ts:46-75`). The portal landing page also surfaces two payment doors, for an outstanding asset fee and for an approved-awaiting-payment retention request, each re-verifying the fee server-side and hard-gating on any outstanding asset waiver document before building a Stripe Checkout session (`src/routes/(site)/my-account/+page.server.ts:189-255`).

Every request the code actually creates carries `kind: 'new'`. The "retention" kind (a year-to-year re-ask intended to surface during renewal) is fully typed and has a dedicated admin approval function, `approveRetentionRequest`, but no code path anywhere ever creates a request with `kind: 'retention'` (`src/routes/(site)/my-account/gear/+page.server.ts:68-74`; `src/member-portal/lib/assets.ts:339-354`; confirmed by grep across `src/`). The renewal route, `/my-account/renew`, contains only membership-tier renewal and checkout logic; it never imports or calls `createAssetRequest` and contains no mention of retention (`src/routes/(site)/my-account/renew/+page.server.ts:1-113`).

No email or notification fires anywhere in this lifecycle: not on submission, not on approval or denial, not on payment resolution. A grep for email/notify across the request-handling code returns nothing; admin discovery of a new request happens only through a manual visit to the requests inbox or its sidebar badge count (`src/member-portal/lib/assets.ts`; `src/routes/admin/club/asset-requests/+page.server.ts`; badge wiring at `src/theme/admin-attention.ts:22,44-45,130`).

Releasing a held assignment, whether by member self-release or admin action, never touches the waitlist. `releaseAssignment` is a bare status update with no read of or write to `asset_waitlist`; promoting the next waitlisted household is not automated anywhere in this code (`src/admin-club/lib/assets-store.ts:203-208`; `src/member-portal/lib/assets.ts:190-201`). Members are added to the waitlist only as a side effect of an admin approving a "new" request when no capacity slot is free; there is no member-facing "join the waitlist directly" action distinct from requesting an asset (`src/member-portal/lib/assets.ts:330`; `src/admin-club/lib/assets-store.ts:278-295`).

Both `asset_requests` and `asset_waitlist` hold zero live rows, so this entire member-initiated lifecycle has never been exercised against production data. It is wired end to end all the same: request creation, approval branching, waitlist enqueue, denial.

## What the club's own process appears to be

"Asset," in this codebase and in the club's prior operations, means a seasonal storage assignment (a mooring, RV parking spot, trailered-boat parking spot, or rack slot), not equipment or gear inventory. The prior ops database's four asset types, fees, and capacities match the ones now in `asc-club` (`aksailingclub-legacy/db/backups/asc-ops-20260327-153503.sql:2-12`). There is no per-item equipment checkout-and-return system, no key tracking, and no gear inventory anywhere in either the legacy or new codebase (confirmed by grep of the legacy `ops/` tree).

Member-facing content describes storage as at-owner risk and ungated by anything beyond membership standing plus a use requirement specific to each type: rack items must be "actively used during the sailing season," trailered boats must sail at least three times per season, and mooring/RV waitlists "commonly span multiple years" (`src/content/pages/seasonal-storage.md:15-26`; `src/content/pages/rack-storage.md:23,31`; `src/content/pages/trailered-boat-parking.md:5,23,31`; `src/content/pages/moorings.md:22`). The club's own boat fleet (Lidos, Lasers, Optimists, a few larger keelboats) is a separate, entirely undigitized process: qualification by demonstrated skill, self-logged use on a physical clubhouse whiteboard, and issue reporting through a Discord channel (`src/content/pages/club-boat-use-and-qualification.md:5-21,36-45`). This fleet-qualification process is distinct from the software-tracked "assets" domain and has no database representation.

Historically, expressing interest in storage has been manual: a member uses an Issues & Support form or a Discord channel, and the request routes by email to the relevant committee, not through any booking flow (`src/content/pages/rack-storage.md:16-17,27`; `src/content/pages/moorings.md:26-28`; `src/content/pages/issues-and-support.md:5,21-22,34-36`). Boat/equipment problem reports route to a different Discord channel than storage requests (`src/content/pages/issues-and-support.md:12-13,43`). The legacy ops dashboard's own payments table was a dead, empty ledger; real payment state lived entirely on the assignment row's own payment fields, and the fee an assignment was historically billed at was never snapshotted—the import approximates historical fees using today's rate (`scripts/import/ops-assets.README.md:103-106,113`). The legacy dashboard's Stripe payment-link-and-email route for asset fees (`POST /api/assignments/:id/send-payment`) remains live and was deliberately excluded from the routes retired elsewhere in that system, meaning it is still relied on today (`docs/plans/assets/ops-events-410.md:1-11` and its diff context). Whether or how that legacy payment-request flow has a counterpart in the new site was not verified in this read.

## Settled decisions and open queue items that constrain a rebuild

Assets is queued as an admin-screen-pass in the standing series and is simultaneously running as cairn's design-capture trial; five pre-trial chores are already done and the perimeter (`/admin/club/assets`, `/admin/club/asset-requests`) is currently audit-error-clean (`docs/STATUS.md`, 2026-07-29 entry; `docs/plans/2026-07-29-cairn-design-trial-assets.md:1-9`; `docs/design-benchmark/2026-07-29-assets-trial-log.md:118,140,201,208`). Geoff has ruled that Assets gets a functional-analysis-first pass, same disposition as Money and Classes, but called it "closer to salvageable" than either (`docs/2026-07-20-admin-toolkit-catalog.md:158-165`).

The asset_types id mismatch (underscore vs hyphen) is a logged, unfixed defect explicitly named to ride along with this pass, with a fix direction already named favoring migrating the database ids rather than the code, on the reasoning that `asc-club`'s schema is fully evolvable (`ROADMAP.md:59`; `docs/status-archive.md:251-260`).

An older measurement (2026-07-16) recorded zero requests ever filed, zero waitlist rows, 40 active assignments across 148 households, and single-digit release/request activity per season club-wide, and this low-volume finding is why the member-facing release/request/cancel actions were placed on a dedicated portal page rather than landing-page chrome (`docs/design-benchmark/decisions.md:238-249`). A previously-ratified probe once depicted asset data the system cannot produce—a fictional "Gear locker" type and fictional slot ids—when every real assignment instead carries a free-text description of the member's own boat; the standing lesson is to ground any Assets probe against real rows and both themes before ratifying it (`docs/status-archive.md:556-565`).

The 2026-07-07 member-portal design spec already specs the request lifecycle as a small state machine (pending → queued|assigned|denied) reusing the waitlist table and an offer-claim token mechanism, and specs retention as request-only, never automatic, requiring admin approval before payment as a deliberate merit check (`docs/2026-07-07-member-portal-design.md:57-90`). The site-wide symmetry rule (every self-service action implies its inverse) is the stated origin of the member-initiated cancel and release actions, added beyond the original spec (`docs/2026-07-07-requirements-adversarial-review.md:78-85`). A category-level finding from that sitting: no membership-management product in the club's category offers season-long asset assignment with waitlist and per-asset billing, which is named as the reason a custom-built system exists here at all (`docs/2026-07-07-membership-functionality-gap-analysis.md:13-16`).

Two parity gaps are named and still open: no admin writer exists to edit an asset type's fee, mirroring the tier-price editor that exists for memberships (`docs/2026-07-07-polish-backlog.md:62-63`; `docs/design-benchmark/polish-triage.md:168-169`); and the class waitlist lacks the manual reorder and notes capability the asset waitlist already has, naming the asset side as the more complete precedent (`docs/2026-07-07-polish-backlog.md:64-65`). A Discord webhook channel for asset events exists on the legacy ops worker but is unwired from the new site—no Discord notification fires for payment requests or waitlist events from this codebase (`docs/2026-07-07-polish-backlog.md:58-59`). Asset-fee collection itself (turning "record that money arrived" into an actual collection mechanism) was named in 2026-07-07 as unbuilt in the new site, since `recordPayment` only logs money already received; this read did not check whether that gap has since closed. Attention badges for the asset-requests queue are already wired through the shared `attention` mechanism alongside committees and the class waitlist, with the Overview strip guaranteed to match by construction (`docs/status-archive.md:152-155`).

One fragility is named for the audit tooling itself, not the product: the page list the audit config checks names content slugs by hand, so a future rename or deletion would silently read as a wrong-but-measured 404 rather than an error, worth knowing before adding pages to that config during this pass (`docs/design-benchmark/2026-07-29-assets-trial-log.md:308-310`).

**A disagreement worth surfacing plainly**: the 2026-07-07 spec and later status notes describe retention as already surfacing "in the renewal flow" as a designed behavior (`docs/2026-07-07-member-portal-design.md:57-90` context), while direct inspection this session finds the renewal route contains no asset-request logic at all and no code path ever creates a retention-kind request (`src/routes/(site)/my-account/renew/+page.server.ts:1-113`; grep across `src/`). The approval machinery for retention exists and is reachable from the admin inbox; nothing upstream of it ever produces a retention request today.

## Open questions only Geoff can settle
